## 2. The ownership defect and the correction

### 2.1 Defect

`DurableRecordStore` works through an injected filesystem: the in-memory
`SyntheticFilesystem`, or the real `PosixFilesystem`. Two of its methods
acquired a descriptor of their own and dropped it.

* **`read_record_bytes`.** It called `openat(…, O_RDONLY)` on the record,
  returned `read(fd)`, and never closed `fd`. It did this on success, and it
  let a read refusal escape without closing.
* **`publish`.** It called `create_file` on `<name>.tmp`, then `write`,
  `fsync`, `renameat` and the entry `fsync`. It never closed the temporary's
  descriptor, on success or on any failure.

Over `PosixFilesystem`, each call left one real kernel descriptor open. That
is one per read and one per publication attempt, in any long-lived process
using the store, not only in the tests.

### 2.2 Correction

* **One owner, `DurableRecordStore._release(number) -> bool`.**
  * Over `PosixFilesystem`, it calls `PosixFilesystem.release` and returns
    its answer. That method's contract is unchanged: the number leaves the
    filesystem's table before `close(2)`, it is never retried, and inventory
    descriptors are never closed.
  * Over the model, `SyntheticFilesystem.close` is the whole release. It
    refuses only a number it never issued, and that refusal becomes `False`.
  * A `ModelRefused` from either becomes `False`.
  * **Why a type test.** The branch is `isinstance(self._fs,
    SyntheticFilesystem)`, not an attribute lookup. `test_no_execution`
    forbids `getattr` on anything but `self` and three named receivers in the
    planning tier, and the planning tier may not import `PosixFilesystem`.
    No guard was changed.
* **`read_record_bytes`.**
  * An `openat` refusal still returns `None`, and nothing was acquired, so
    nothing is released.
  * Otherwise the read runs in a `try`, and `finally` performs the one
    release.
  * A read refusal still propagates, with its own reason.
  * A failed release after a successful read raises `ModelRefused`. That is
    how a failed read already surfaces to every caller. Returning the bytes
    would claim a success the reader could not establish. Returning `None`
    would claim an absent record that is present.
* **`publish`.**
  * A `create_file` refusal returns `not_durable` with no barriers, as
    before. Nothing was acquired, so nothing is released.
  * Otherwise the unchanged sequence runs in one `try`: write, the injected
    `record-data` point, the data barrier, the `rename` point, the rename,
    the `record-entry` point and the entry barrier. `finally` performs the
    one release, **last**.
  * The order and interruption points are therefore unchanged, and
    releasing a descriptor removes no name.
  * A `ModelRefused` in the sequence is collected as a reason, exactly as
    before. A failed release adds its own reason.
  * Any reason gives `published=False` and `refusal=not_durable`.
    `barriers` still lists only the barriers that returned success.
* **No raw `os.close`** was added to `lifecycle_storage.py`. The release
  stays inside the filesystem abstraction.

### 2.3 Ownership table

"Released" means one `_release` call for the store's own descriptor.
Directory descriptors come from `open_directory`: the inventory holds them for
the run and the store never releases them.

| Path | Acquired? | Released | Outcome |
|---|---|---|---|
| read: `openat` refuses | no | never | `None`, as before |
| read: success | yes | once, after the read | the bytes |
| read: `read` refuses | yes | once, before the refusal propagates | the read's `DescriptorRefused`, as before |
| read: success, release fails | yes | once, not retried | `ModelRefused("… was not released …")` |
| read: read refuses, release fails | yes | once, not retried | the read's refusal; the first causal failure wins (§8 Q3) |
| publish: semantic, temporary or exclusivity refusal | no | never | as before |
| publish: `create_file` refuses | no | never | `not_durable`, `barriers=()`, as before |
| publish: `write` refuses | yes | once | `not_durable`, `barriers=()`; temporary left |
| publish: `record-data` injected | yes | once | `not_durable`, `()`; temporary left, no final |
| publish: `rename` injected | yes | once | `not_durable`, `("record-data",)`; temporary left, no final |
| publish: `renameat` refuses | yes | once | `not_durable`, `("record-data",)` |
| publish: `record-entry` injected | yes | once | `not_durable`, `("record-data",)`; final visible, no temporary |
| publish: entry barrier refuses | yes | once | `not_durable`, `("record-data",)` |
| publish: success | yes | once, after the entry barrier | `published`, `("record-data", "record-entry")` |
| publish: success, release fails | yes | once, not retried | `not_durable`, `("record-data", "record-entry")`, one reason naming the failed release; final visible (§8 Q1) |
| publish: any failure, release fails | yes | once, not retried | `not_durable`, the failure's reason **and** the release reason |
| publish or read: an exception that is not `ModelRefused` | yes | once, in `finally` | the exception propagates; a failed release's answer is not reported (§8 Q3) |

## 5. Regression tests

They are in `test_lab_integration.py` §10.

**The oracle.** `_OwnershipFilesystem` subclasses the real `PosixFilesystem`.
It records every descriptor that `create_file` and `openat` return, and every
`release` call. It asserts that no acquired number is handed out again while
it is still held. Faults can be injected per operation:

* `create` and `open` refuse **before** a descriptor exists;
* `read` and `write` refuse **after** one exists;
* `release` performs the real release and then reports failure. Linux frees
  the number even when `close(2)` returns an error, so the test itself leaks
  nothing.

The inventory's two synchronizable descriptors are bound before any
baseline, so a `/proc/self/fd` count measures only the store. That count is a
supplement to the oracle, never the only check.
`_assert_only_its_own_released` requires three things: nothing is still held,
the release calls equal the acquisitions, and no inventory descriptor was
ever released.

## 8. Focused questions for Codex re-review

1. **A failed release after full success is `not_durable`.**
   * Both barriers returned success. `refusal=not_durable` is kept because
     the existing vocabulary has no better truthful member.
   * `published=False` is the fail-closed reading, and `close(2)` can be the
     only report of an earlier error.
   * The state left is R3-1's: the record is visible, the writer refuses, and
     successors re-seal.
   * The enum docstring still says *"A barrier did not return success"*.
   * Should this instead be one additive member, such as
     `descriptor_not_released`? Or should the release move before the rename,
     the classic write, fsync, close, rename order, so that a failed close
     leaves the unpublished `rename`-point state? Either changes the
     contract's vocabulary or order, so I did neither without direction.
2. **The model dispatch is `isinstance(…, SyntheticFilesystem)`.** It is used
   because the planning-tier guard forbids `getattr` on `self._fs`, and
   `durability_model.py` was not an authorized file. The alternative is to
   add `release()` to `SyntheticFilesystem` under a later assignment. Is the
   type test acceptable?
3. **The first causal failure wins.** When a read refuses, or an exception
   that is not `ModelRefused` propagates, a failed release's answer is not
   reported. The call already refuses. `publish` reports both for
   `ModelRefused` failures. Is that sufficient for the read path?
4. **The descriptors.py observations (§2.4).** Should the `create_file` and
   `openat` post-open leaks become their own bounded assignment? They are
   unreachable from the store today.
5. **The acquisition guards pass on both stores.** That is by construction:
   the old store released nothing. They pin the new rule "no release without
   acquisition", and they are not regressions of the old defect. Is that
   classification acceptable?
6. **Headroom.** Rows 6 to 8 show net zero for the whole package. Does this
   discharge R1's §7.5 risk note?
