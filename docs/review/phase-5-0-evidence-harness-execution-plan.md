control on the ownership route and is labelled as such in the record.

succeeding where it must refuse, is reported to the Security Reviewer
immediately and the rehearsal stops: it would require a design revision.

## 6. Cleanup — exact, bounded, reverse dependency order

Generated by `cleanup.CleanupPlan.for_mutations()` from the declared mutations of
§2, **in the exact reverse of the order they were declared**. Nobody writes a
cleanup command in this harness, which is why no cleanup command can be recursive:
the generator has one entry per mutation kind, and every entry removes one named
object.

**The configuration phase is hoisted to the front**, ahead of every other
reversal. Restoring `pg_hba.conf` and `pg_ident.conf` puts bytes back on disk; it
does not make them the running server's effective configuration, because
PostgreSQL parses them at startup and on `SIGHUP` and until it is told to re-read
them it keeps authenticating with the harness's temporary rules in memory. So the
phase is restore → **one** reload → the bounded post-reload observation, and it
precedes every step whose safety depends on the restored authentication — the
`DROP ROLE` and `DROP DATABASE` reversals connect under the restored rules and
not under the harness's.

| Order | Kind | Reverses | Argument vector | Exits meaning "satisfied" |
|---|---|---|---|---|
| CL-01 | restore | M-26 | `/usr/bin/install --mode 0640 --owner postgres --group postgres <TARGET_ROOT>/before/pg_ident.conf <PG_CONFIG_DIR>/pg_ident.conf` | 0 |
| CL-02 | restore | M-25 | `/usr/bin/install --mode 0640 --owner postgres --group postgres <TARGET_ROOT>/before/pg_hba.conf <PG_CONFIG_DIR>/pg_hba.conf` | 0 |
| CL-03 | **reload** | — | `/usr/bin/psql --no-psqlrc --no-password --set ON_ERROR_STOP=1 --host <PG_SOCKET_DIR> --dbname postgres --command SELECT pg_reload_conf()` | 0 |
| CL-04 | **verify** (control) | — | the same vector with `--command SELECT 1`, as `postgres` | 0 |
| CL-05 | **verify** (proof) | — | the same vector as **`freedomcoord`**, `--dbname <EVIDENCE_DB> --username freedom_migration_coordinator --command SELECT 1` | **any non-zero**; 0 means the temporary mapping is still effective |
| CL-06 | reversal | M-27 | `/usr/bin/systemctl stop fb-evidence-s4.service` | 0, 5 |
| CL-07 | reversal | M-24 | `/usr/bin/psql --no-psqlrc --set ON_ERROR_STOP=1 --dbname <EVIDENCE_DB> --command DROP ROLE IF EXISTS freedom_migration_coordinator` | 0 |
| CL-08 | reversal | M-23 | `/usr/bin/psql --no-psqlrc --set ON_ERROR_STOP=1 --dbname postgres --command DROP DATABASE IF EXISTS <EVIDENCE_DB>` | 0 |
| CL-09 … | reversal | M-22 … M-17 | `/usr/bin/chattr -i -a -- <path>` then `/usr/bin/rm --force -- <path>`, one named path each | 0 |
| … | reversal | M-16 … M-10 | `/usr/bin/rmdir -- <path>`, deepest first | 0 |
| … | reversal | M-09, M-08 | `/usr/sbin/gpasswd --delete freedomsheet freedomjournal`, then `freedomcoord` | 0, 3 |
| … | reversal | M-07 … M-05 | `/usr/sbin/userdel fbprobe`, `freedomsheet`, `freedomcoord` | 0, 6 |
| CL-last | reversal | M-04 … M-01 | `/usr/sbin/groupdel fbprobe`, `freedomsheet`, `freedomcoord`, `freedomjournal` | 0, 6 |

**Why the verification is two steps.** A refusal on its own attributes nothing —
the same rule every evidence band lives by. CL-04 is the **control**: an ordinary
local connection as `postgres` must still succeed, which excludes *"the server is
down"*, *"the socket moved"* and *"the configuration failed to parse"* as
explanations. CL-05 is the **proof**: it must be **refused**. It runs while the
temporary role still exists — before CL-07's `DROP ROLE`, which is why the drop
steps come after — so the refusal is attributable to the removed mapping and not
to a role that no longer exists. Neither step reads, prints or returns any
configuration, rule text, address, method or credential: one is `SELECT 1`, the
other is whether `SELECT 1` was refused.

**A zero exit from CL-03 is not evidence.** `pg_reload_conf()` returns as soon as
the signal is sent; it reports neither that the files parsed nor that the new
rules are in force. Cleanup completion therefore depends on the restore, reload,
control and proof **observations**, never on exit status alone, and any of them
failing or not being made is state **S-B** with the effective-configuration risk
named in full.

**A partial setup that reached only one configuration file still gets the whole
phase over that file** — the restore that was reached, the one reload, the
control and the applicable proof. There is no path on which a file is restored
and not reloaded, and none on which a reload is performed and nothing observed
after it.

**Properties, each checked by the suite rather than asserted here.**

- **No recursion is expressible.** `-r`, `-R`, `-rf`, `--recursive`,
  `--no-preserve-root`, `-a` and `*` are refused in any generated argv; a
  directory is removed with `rmdir`, which removes only an empty one; a file with
  `rm --force` on one named path.
- **Nothing outside the target.** Every path passes
  `DisposableTarget.contained_path()`, except `<PG_CONFIG_DIR>/pg_hba.conf` and
  `pg_ident.conf`, which pass `config_path()` — two filenames, and no third.
- **Re-runnable.** No step performs a destructive act when its object is absent,
  and every `psql` **reversal** carries `IF EXISTS`. The reload and the two
  verification steps are re-runnable for a different reason: they create and
  remove nothing at all.
- **Configuration is restored, not edited.** The two config files are reinstalled
  from the byte-exact capture taken at B6-01/B6-02, so cleanup restores the
  recorded starting state rather than deleting a line by pattern.
- **Restoring a file is not restoring effective configuration.** One reload
  follows every restore, and the bounded post-reload observation follows the
  reload. Cleanup is not complete until all four have been observed.
- **The mapping the proof needs exists before the plan does.** A configuration
  mutation carries its complete `(identity, role)` pair or is refused at
  declaration, so no blank identity, username or role can reach a cleanup step
  and no half is defaulted.

**Cleanup failure is a stop condition, and it is not retried.** §2.13.2b:

| State | Reached when | Exit | What happens next |
|---|---|---|---|
| **S-C** | all stages passed, both transient directories removed | 0 | proceed |
| **S-A** | a stage failed or was inconclusive, cleanup completed | **2** | no residue, no generation artifact, no row |
| **S-B** | cleanup could not remove some artifact, **or could not prove the temporary authentication configuration gone**, whether or not a stage also failed | **3** | each remaining artifact named by absolute path with the operation and its `errno`; every unresolved effective-configuration risk named in full; **the next invocation refuses while they exist and does not clean them**; recovery is the named operator procedure |

The claims are deliberately separate: *"no generation or database artifact"* is
unconditional and survives every state; *"no transient residue"* is **conditional
on cleanup succeeding**, and stating it unconditionally is the defect §2.13.2b
exists to correct. The third claim — *"the temporary authentication configuration
is no longer effective"* — is conditional on the restore, the reload **and** the
post-reload observation, and a temporary rule that may still be in force produces
S-B on its own: it is residue that has no path.

## 8. Evidence artifact produced by each band

Each band emits `EvidenceRecord`s serialized by `records.serialize_records()` —
sorted keys, fixed separators, a trailing newline, so two runs over the same
observations produce byte-identical bytes — and referenced by
`records_digest()`, a SHA-256 over those bytes in the canonical typed encoding
`application/idempotency.py` establishes.

| Band | Records | Artifact |
|---|---|---|
| 0 | `SudoersAnalysis`, `HbaAnalysis`, `IdentAnalysis` findings | `phase-5-0-evidence-band-0-discovery.json` |
| 2 | `JNL-52-GROUP-*`, `JNL-52-ID-*`, `JNL-52` access cases | `phase-5-0-evidence-band-2-identity.json` |
| 4 | `C-1 … C-6`, `P-1 … P-9`, `M-1`, `M-2`, `S4-0 … S4-3` | `phase-5-0-evidence-band-4-probe.json` |
| 5 | `CAP-LAUNCHER-BND`, `CAP-E7-ENVIRONMENT`, `JNL-49`/`JNL-50` cases | `phase-5-0-evidence-band-5-capability.json` |
| 6 | HBA/ident post-change analysis, denial matrix | `phase-5-0-evidence-band-6-postgresql.json` |
| 7 | `JNL-46-*`, `JNL-51-*`, `JNL-53-*`, journal lifecycle, recovery | `phase-5-0-evidence-band-7-journal.json` |

Every record carries `schema_version` **3** as its first field, and an artifact
whose version is not this harness's is refused rather than compared with one this
harness produced. Version 3 is the version in which a record declares a
`case_role` — `control`, `dependent` or `standalone` — and in which the
caller-supplied `positive_control_status` is **gone from the schema**: a dependent
record stores only the control's `positive_control_case_id`, and the control's
status is read off the control's own record.

Reading an artifact back is a **check**, not a parse: `deserialize_records()`
resolves every control reference against the other records in the same artifact
**before** it constructs anything — refusing a missing, duplicated,
self-referential, cyclic, cross-band or inadmissible reference — and then
recomputes each record's status and reason from its stored observations and its
resolved control, refusing a stored value that disagrees. There is no stored
control status to compare, and therefore none to tamper with.
