## 2. Requirements implemented (prompt §2)

| Requirement | Where |
|---|---|
| Release the acquired descriptor exactly once on every failure before return | `try … except BaseException: self._abandon(fd); raise` wrapping `_track(…, _identity(fd), …)` in both methods, plus the `write` in `create_file` |
| Never retry a failed close | `_abandon` calls `os.close(fd)` once and swallows `OSError` |
| Remove any partially registered descriptor from the tracking table first | `_abandon` pops `fd` from `_descriptors` before `close` |
| Preserve and re-raise the first causal failure | bare `raise` in the `except` block; the close error is caught inside `_abandon`, so it is neither raised nor chained |
| No unlink, rename, truncate, retry or repair of a pathname | `_abandon` performs only `dict.pop` and `os.close` |
| Do not release inventory descriptors | `_abandon` only ever receives the number `os.open` just returned in the same call (§3) |
| Success behaviour unchanged | the success path executes the same `_track` and `write` calls in the same order; flags, creation mode, refusal mapping of `os.open` errors and returned metadata are untouched |

`except BaseException` is deliberate: an interrupt (for example
`KeyboardInterrupt`) arriving between `os.open` and the return is also a failure
before hand-off, and would otherwise leak. The exception still propagates
unchanged.

## 3. Descriptor-ownership reasoning

* **Before `os.open` returns**, nothing is owned. An `os.open` failure is mapped
  to `DescriptorRefused` exactly as before and nothing is released.
* **Between `os.open` and `return`**, the method is the sole owner. No other
  reference exists: `_track` stores the number in `_descriptors`, but the
  `Descriptor` has not reached a caller. `_abandon` removes that entry and
  closes the number.
* **After `return`**, the caller owns it and releases it through
  `PosixFilesystem.release`/`close` as before. `release`'s contract is
  unchanged.
* **Why an inventory descriptor cannot be closed.** The number was allocated
  by the kernel in this call while every inventory descriptor was still open,
  so it cannot equal one. `_abandon` receives no other number. The test oracle
  additionally asserts that neither of the inventory's two descriptors appears
  among the recorded closes.
* **Why not route through `release`.** `release` looks the number up with
  `_descriptor`, which refuses an unregistered number; in the identity-failure
  path `_track` never ran, so `release` would raise `DESCRIPTOR_NOT_REGISTERED`
  and replace the causal failure. It also returns a boolean the failing caller
  has no use for. `_abandon` is the minimal primitive for a number this object
  holds but has not issued.
* **Close failure.** Linux frees the number even when `close(2)` reports an
  error, so a retry could close a number since reused elsewhere. It is reported
  nowhere, because the caller already receives a failure and the first causal
  one is the required report (prompt §2). Compare R2 §8 Q3, where the same
  precedence was chosen for the store's read path.
* **Pathname state.** A name `O_EXCL` created stays as the failure left it: an
  empty file after an identity failure; the partially written prefix after a
  write failure. No mutation conceals it.

## 8. Security implications

* Positive: a long-lived process using `PosixFilesystem` can no longer
  accumulate descriptors (and with them open references to created or opened
  objects) through repeated identity or initial-write failures; the leak would
  eventually refuse unrelated opens with `EMFILE`.
* No new path resolution, no pathname mutation and no change to flags,
  creation mode or `O_NOFOLLOW`. Refusal classifications and messages are
  unchanged, so no path or OS message reaches an operator-facing refusal.
* Not retrying a failed close avoids closing a reused descriptor number.
* The raw `OSError` from a failed `fstat` still propagates unwrapped, exactly as
  before; this was not reclassified because the prompt requires unchanged
  refusal classifications (§10 Q2).
