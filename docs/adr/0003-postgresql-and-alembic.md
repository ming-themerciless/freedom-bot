## Context

Google Sheets is the current operational store. Phase 0 discovery found concrete
failure modes that a spreadsheet cannot fix:

- **Whole-row overwrite.** Every mutating command rewrites 26 cells regardless of
  what changed, so any concurrent Council edit to level, badge, mission count or
  last-played is silently lost
  ([command-inventory.md §4](../discovery/command-inventory.md#4-the-fixed-write-set)).
- **No concurrency control.** The sheet has no version column, and
  `application/actor_locks.py` serialises within one process only. The web app
  will be a second process.
- **No transactions across actors.** `/trade` relies on a single Google
  `batchUpdate` call being all-or-nothing; nothing else can.
- **No audit trail.**
- **Name as identity.** Characters are looked up by a case-insensitive match on
  column A, first match wins (`models/actor.py:77`).
- **Silent row cap** at `A3:AL150`.
- **Read amplification.** Every command reads the entire table for one row.

`.agents/AGENTS.md` and plan §3 already name PostgreSQL. This ADR records the
scope, the migration tool and the conventions that Phase 1 will be reviewed
against.

## Decision

### PostgreSQL is the authoritative operational store

Production runs PostgreSQL. SQLite is acceptable for isolated unit tests that
touch no schema, but **repository and migration tests run against real
PostgreSQL** — plan §12 Phase 1 requires "migrations apply to an empty database"
and "constraints reject invalid data", neither of which SQLite can demonstrate
for PostgreSQL-specific types and constraints.

### SQLAlchemy 2.x Core and ORM, with explicit mapping

The ORM is an adapter concern. Domain objects are constructed **from** ORM rows by
explicit mapper functions in `adapters/database/`; they are never ORM instances.
`.agents/AGENTS.md`: *"Keep ORM records and database sessions outside the domain.
Map explicitly between persistence and domain models."*

Practically: no lazy-loading relationship may cross into domain code, because a
lazy load in a domain method is an invisible query — and a source of the N+1
problem the same document forbids.

### Alembic for migrations

- Every schema change is a committed migration.
- An applied migration is **never** edited. Roll forward, or write a documented
  recovery migration (plan §14.3).
- Migrations are reviewed for reversibility. Where a downgrade would lose data,
  the migration says so explicitly rather than pretending to be reversible.
- Every migration is tested against an empty database and against a database
  holding the previous revision's fixtures.

### Schema conventions

Binding for Phase 1 review:

| Convention | Rule |
|---|---|
| Primary keys | UUID (`uuid7` preferred for index locality; `uuid4` acceptable), generated by the application at insert time, **never derived from external data** — see below |
| Discord snowflakes | `BIGINT`. Never `INTEGER` — snowflakes exceed 2³¹ |
| Timestamps | `TIMESTAMPTZ`, always UTC, always timezone-aware in Python |
| Money | `BIGINT` copper — see [ADR 0005](0005-identifier-and-quantity-representation.md) |
| Divisible quantities | integer smallest unit — see ADR 0005 |
| Enumerations | text with a `CHECK` constraint, or a lookup table. **Not** PostgreSQL `ENUM` types, which are painful to alter in a migration |
| Mutable aggregates | `version INTEGER NOT NULL DEFAULT 0` for optimistic concurrency |
| Audit tables | append-only; no `UPDATE` or `DELETE` grant for the application role |
| Foreign keys | always declared, with explicit `ON DELETE` behaviour |
| Nullability | `NOT NULL` by default; a nullable column must have a stated reason |
| Naming | `snake_case`, plural table names, matching plan §7 |

### Identifier assignment and import idempotency

**Decided 2026-07-30.** A character's ID is assigned when its row is created. It is
not computed from the sheet row number, the character name, the Foundry actor ID, or
anything else outside the database. Nothing external can therefore change it.

**Re-running an import does not duplicate**, because uniqueness lives in the mapping
tables rather than in the ID:

```text
sheet_row_mappings      UNIQUE (sheet_tab, row_index)      -> character_id
external_actor_mappings UNIQUE (world_id, external_actor_id) -> character_id
```

The importer, in one transaction: look up the mapping; if it exists, reuse the
`character_id` it points at and update; if not, generate an ID, insert the character,
insert the mapping. Idempotency is then a database constraint — something the store
enforces — rather than a property of a hash function the importer must get right
every time.

Two consequences worth stating, because they are why this was worth deciding:

- **A Foundry world rebuild does not break identity.** It invalidates every actor
  `_id`, but the platform ID is independent of it, so re-linking replaces a mapping
  row and leaves the character untouched.
- **IDs are unguessable**, which matters once they appear in web URLs (plan §5.2).

### Transaction boundary

One use case, one transaction, opened by the application service and never by
domain code or an adapter. A repository method participates in the caller's
transaction; it does not commit.

This is what makes plan §12 Phase 5's "trade/crafting cannot partially apply"
testable rather than aspirational.

### Database role

The application connects as a restricted role (plan §9.3): `SELECT`, `INSERT`,
`UPDATE`, `DELETE` on operational tables; `SELECT`, `INSERT` only on audit tables;
no `CREATE`, no superuser. Migrations run as a separate, more privileged role
invoked by the deployment, not by the running application.

## Consequences

**Positive.**

- Constraints move invariants into the store: a negative balance, a duplicate
  character link or an orphaned mapping become impossible rather than merely
  unlikely.
- Optimistic version columns make the "stale optimistic version" and "concurrent
  trade/edit" scenarios in plan §13.2 real, detectable conditions.
- The append-only audit tables give the Council the correction-not-erasure model
  `.agents/AGENTS.md` requires.

**Negative.**

- A new operational component: backups, restore drills, connection limits and
  monitoring (plan §14.3). None exists today.
- Integration tests need a real PostgreSQL, so CI and the development setup get
  more complex than `pytest` against pure functions.
- Application-generated UUIDs are larger and less cache-friendly than bigserial
  keys. Accepted deliberately: IDs must be stable and mergeable across imports
  from two external systems, and a sequence-generated integer is neither.

## Alternatives considered

**SQLite in production.** Rejected: two processes writing concurrently, plus the
locking behaviour that implies. `.agents/AGENTS.md` explicitly forbids relying on
SQLite-only behaviour in production code.

**Database-generated `bigserial` keys.** Rejected — but *not* for the reason this ADR
originally gave. The original text claimed idempotency needs an ID computable before
writing, which contradicted the random-UUID convention above; that reasoning is
withdrawn (OD-35). The actual reasons are that a sequence integer is guessable and
enumerable in a web URL, and that merging records originating in two external systems
is easier when the key carries no ordering meaning. Idempotency itself is delivered by
the mapping-table constraints, which work identically with either key type.

**Deterministic UUIDv5 keys**, derived from the sheet row or the Foundry actor ID.
Rejected: it welds identity to external keys that are **not stable** — a row reorder
or a Foundry world rebuild would change the identity, which is precisely what a stable
ID exists to prevent. It also makes IDs guessable from a known name or row number.

**Raw SQL with no ORM.** Considered seriously — it would guarantee the domain
stays clean. Rejected because Alembic's autogenerate and SQLAlchemy's type
handling remove a large class of hand-written migration errors, and the explicit
mapping rule above already achieves the isolation.

**PostgreSQL `ENUM` types.** Rejected: adding a value requires `ALTER TYPE`, which
does not roll back cleanly inside a transaction in older versions and complicates
downgrade paths. `CHECK` constraints and lookup tables are boring and reversible.
