Revised 2026-08-13 by the P3.0 remediation: SM-05's attempt semantics were

Amended 2026-08-14 by the OD-44 re-review remediation, **by addition only**:
SM-01 gains the provider-binding forbidden transition, and SM-02 gains the
rotation-integrity mechanism and its four forbidden transitions. No earlier row
was rewritten except SM-02's rotation *mechanism* cell, which now names the

Amended 2026-08-15 by the OD-44 session-lifetime remediation. SM-02's rotation
and idle-refresh *mechanism* cells and its `expired` row are corrected, and two
forbidden transitions are added — reviving an expired-but-unmarked session, and
giving a break-glass session the ordinary idle window. The earlier text said a
rotation required a *live* predecessor while the code tested only
`revoked_at IS NULL`, and said an idle refresh applied N-06 without qualification;
both were **inaccurate as written**, and the corrected cells say what the
statements enforce. No state, trigger or accepted numeric value changes.

Amended twice more on 2026-08-15, by the second and third session-lifetime
reviews, each time because the *mechanism* named in the idle-refresh cell and in
the "break-glass session receiving the ordinary idle window" row did not do what
the cell claimed. The second review found that the `expected_auth_method`
equality predicate refused a false method and could not see a false duration
beside a true one. The third found that removing both arguments had moved the
same authority into `SessionIdlePolicy`'s public dataclass constructor, which
accepted a complete, duplicate-free, positive — and semantically false — mapping
that gave every method the ordinary window. Both cells now describe a
classification derived inside the policy from `AuthMethod.is_break_glass`, from a
policy with no public constructor. Again, no state, trigger or accepted numeric
value changes: this is an interface and composition correction.

Amended a **fourth** time on 2026-08-15, by the idle-policy-construction review,
and this time the shape changes rather than the wording. Three counterexamples
survived the third correction: a directly constructed `SessionSettings` with
`emergency_idle_minutes=60` was an accepted object, so closing the policy's
constructor achieved nothing while the numbers it read were unconstrained (F1); the
refresh statement was generated by iterating the policy's public, overridable
`__iter__`, so an ordinary subclass replaced the SQL's mapping while `for_method()`
went on reporting fifteen minutes (F2); and `SessionService` accepted a policy
beside the repository without requiring them to be the same, so a supported caller
could build a graph that created sessions under one window and refreshed them under
another (F3). `SessionIdlePolicy` is **deleted**. `SessionSettings` validates the
accepted register in its own constructor; `SessionRepository` *derives* a
`SessionPolicy` from it and owns it; `SessionService` reads that policy from the
repository and has no policy argument; and which window a method gets is an
explicit classification table in `application/web/capabilities.py` that refuses an
unclassified method at startup and at construction. Still no state, trigger or
accepted numeric value changes.

Numbers are `N-nn` from
[`phase-3-numeric-policy-register.md`](phase-3-numeric-policy-register.md);
tables are in [`phase-3-logical-schema.md`](phase-3-logical-schema.md).

## 0. How to read these

Each machine states its **states**, its **permitted transitions**, its
**forbidden transitions** and its behaviour under six failure modes the delivery
plan requires to be explicit: process restart, retry, lost response, expired
lease, concurrent action, provider outage and audit failure.

A forbidden transition is not merely "the code should not do this". Each one names
the mechanism that makes it impossible — a constraint, a single-statement
conditional update, or a trigger. Where the mechanism is only a test, it says so.

## SM-01 — OAuth attempt and callback

### States

```text
                    ┌──────────┐
   R-03 ──────────▶ │ pending  │
                    └────┬─────┘
        ┌────────────────┼─────────────────┬──────────────────┐
        ▼                ▼                 ▼                  ▼
   ┌─────────┐     ┌───────────┐     ┌──────────┐      ┌────────────┐
   │consumed │     │  expired  │     │ refused  │      │ superseded │
   └────┬────┘     └───────────┘     └──────────┘      └────────────┘
        ▼
   ┌───────────┐
   │ completed │
   └───────────┘
```

`pending` is a row in `oauth_transactions`. `consumed` means verifier recovery
and erasure succeeded; `completed` means that consumed row was atomically claimed
by exactly one Discord OAuth session. A consumed row may remain uncompleted after
provider refusal or process death; it can never be reused.

### Transitions

| From | To | Trigger | Mechanism |
|---|---|---|---|
| — | `pending` | R-03 after the N-18 limit passes | Insert with `expires_at = now() + N-04` |
| `pending` | `consumed` | R-04 with matching cookie and state | `UPDATE … SET consumed_at = now() WHERE id = $1 AND consumed_at IS NULL AND expires_at > now() RETURNING` |
| `consumed` | `completed` | Provider verification succeeds | In one provider-I/O-free transaction, atomically set `completion_claimed_at`, create the session carrying the transaction id and write the success audit; all commit or none do |
| `pending` | `expired` | Time | No writer; readers compare `expires_at` |
| `pending` | `refused` | State mismatch, missing cookie, provider error | Consumption statement returns zero rows, or validation fails before it runs |
| `pending` | `superseded` | A second R-03 from the same browser | The cookie now names a different transaction; the old row expires unread |

### Forbidden

| Forbidden | Why it cannot happen |
|---|---|
| `consumed` → `consumed` (replay) | The conditional `UPDATE` matches zero rows the second time. This is a database guarantee, not an application check |
| The PKCE verifier being used twice | The consumption statement returns the pre-update ciphertext **and** nulls the columns in one pass (schema §9.2.1). After one callback there is no verifier left to recover, whatever the caller presents |
| A verifier decrypting under a different transaction | The GCM additional authenticated data binds `(transaction id, key_version, provider_key)`; a moved ciphertext fails to authenticate rather than decrypting into the wrong flow |
| The verifier or the state appearing in plaintext at rest | `state` is stored only as a SHA-256 hash; the verifier only as ciphertext. `CHECK (consumed_at IS NULL OR pkce_verifier_ciphertext IS NULL)` keeps that true after use as well |
| `expired` → `consumed` | `expires_at > now()` is in the same statement's `WHERE` |
| A Discord OAuth session created without one uniquely claimed consumed transaction | `sessions.oauth_transaction_id` is required for `discord_oauth`, foreign-keyed `RESTRICT`, and unique among the sessions a completion creates (`WHERE rotated_from_session_id IS NULL`, so an N-08 rotation of the same login is still possible — schema §9.1); the completion claim, session insert and success audit share one transaction after provider I/O |
| A completion spending a transaction started with a **different provider** (added 2026-08-14, OD-44 §8.1) | The claim includes `provider_key = :provider_key`, and the expected key is derived from `VerifiedCompletion` — one indivisible verified result whose identity and tokens must name the same provider, each stamped by the adapter that made the network call. A mismatch matches zero rows and is the same typed refusal as an unknown id: no account, identity, membership projection, token grant, session or success audit, and the transaction is left consumed-and-unclaimed |
| Redirect to an off-site return target | `return_path` is check-constrained to `'/%'` and not `'//%'` (schema §9.2), and re-validated against the allowlist at use |
| A transaction consumed by a different browser | The `__Host-fb_login_txn` cookie is required and its id must match the row |

### Failure behaviour

- **Restart:** transactions live in PostgreSQL; a restart between R-03 and R-04
  changes nothing.
- **Lost response:** the browser never receives the redirect; the transaction
  expires in ≤ N-04 and the user retries. No session exists.
- **Provider outage** at token exchange: `refused`, VM-01 shows the degraded
  banner, the row remains consumed but uncompleted, no session exists, and the
  emergency route (SM-03) remains available.
- **Process death after consumption:** no session exists. The consumed row cannot
  be replayed and is reaped under the existing retention rule; the user retries
  with a new transaction.
- **Concurrent callbacks** with the same code: one consumes, the other gets zero
  rows and is refused.
- **Audit failure:** the login audit event is written in the same transaction as
  the session insert. If it fails, the session is not created and the user sees a
  safe error — a login that cannot be recorded does not happen.

## SM-02 — Authenticated session

### States

```text
   ┌────────┐  privilege change   ┌──────────┐
   │ active │ ──────────────────▶ │ rotated  │ (old row, terminal)
   └───┬────┘                     └──────────┘
       │  logout / operator / limit        ▲
       ├──────────────────────────▶ ┌──────┴────┐
       │                            │  revoked  │
       │  idle N-06 / absolute N-07 └───────────┘
       └──────────────────────────▶ ┌───────────┐
                                    │  expired  │
                                    └───────────┘
```

Every rotation **creates a new `active` row** and terminates the old one; a
session row's id never changes.

### Transitions

| From | To | Trigger | Mechanism |
|---|---|---|---|
| — | `active` | Successful authentication | Insert; `token_hash` unique |
| `active` | `rotated` | `privilege_fingerprint` differs from the resolved capability set (N-08) | One transactional operation (`SessionRepository.rotate()`, added 2026-08-14): the predecessor is read `FOR UPDATE` and required to be live and unrotated, the successor is inserted from that locked row's own account, authentication method and OAuth binding, and the predecessor is revoked — all in the same transaction. **Live means unrevoked *and* `idle_expires_at > now` *and* `absolute_expires_at > now`, tested in the locked read itself** (corrected 2026-08-14): a caller holding a record resolved while the session was valid must not be able to rotate it afterwards. The successor **inherits the predecessor's `absolute_expires_at` exactly** and its idle window is clamped to that inheritance, so the whole chain from one login carries the one bound that login set and no rotation extends it (N-07, N-15). A `discord_oauth` session **carries its `oauth_transaction_id` forward**: the rotated row is the same login and takes no second completion claim (OD-44). A predecessor that is unknown, revoked, idle-expired, absolute-expired, already rotated or another account's yields a typed `SessionRotationRefused` |
| `active` | `revoked` | R-05, C-07, N-66 limit, or detected compromise | `UPDATE … SET revoked_at, revocation_reason` |
| `active` | `expired` | `now() > idle_expires_at` or `> absolute_expires_at` | Evaluated on read; the row is marked on the request that observes it. Being *unmarked* is not being live: an expired row stays unrevoked until some read observes it, so every operation that continues a session tests liveness itself rather than trusting the absence of `revoked_at` |
| `active` | `active` | Ordinary request | One conditional operation (`SessionRepository.touch()`, corrected 2026-08-15): a single `UPDATE` that matches only while the row is unrevoked and **strictly inside both bounds** (`idle_expires_at > now`, `absolute_expires_at > now`; equality at either is expired), sets `idle_expires_at = LEAST(now + idle, absolute_expires_at)` and **never writes `absolute_expires_at`**. The idle duration is **N-06 for `discord_oauth` and N-15 for `webauthn` and `recovery_grant`**, selected inside that statement by `CASE auth_method` from the bounds the repository was constructed with — **amended 2026-08-15 (second session-lifetime review): the duration is not a parameter of the operation at any layer**, having previously been an `idle` argument beside an `expected_auth_method` argument that verified only the method. The refresh takes a session id and an instant. **Amended again 2026-08-15 (third session-lifetime review): nor is the mapping a parameter of the policy's construction.** **Amended a fourth time 2026-08-15 (idle-policy-construction review): nor is there a policy object to construct.** `SessionIdlePolicy` is deleted. `SessionRepository(connection, settings=SessionSettings)` derives a `SessionPolicy` itself — `SessionSettings` validates the accepted register in its own constructor, so the numbers are in-register whatever built it — and the `CASE` branches are generated by walking `AuthMethod` and asking `session_class_of()`, an explicit table, rather than by iterating anything the caller supplied. `SessionService` takes its bounds from that repository and has no policy argument, so a graph cannot hold two bounds sources. Zero rows matched is a typed `SessionTouchRefused`, never a silent success |

### Forbidden

| Forbidden | Mechanism |
|---|---|
| Extension beyond the absolute bound | `CHECK (idle_expires_at <= absolute_expires_at)` plus the same clamp in the update statement. Neither an idle refresh nor a rotation writes `absolute_expires_at` at all: touch omits it from its `SET` clause, and a rotation inherits the predecessor's value, so the bound is written once, by the login |
| A revoked or expired session serving a request | Resolution filters on both on every request; there is no cache of "session was valid" |
| **An expired-but-unmarked session being revived by a continuation** (added 2026-08-15) | `revoked_at IS NULL` establishes only that nobody *ended* the session, and is **not** liveness. Both continuation operations — `rotate()` and `touch()` — carry both expiry comparisons in the same conditional statement that performs the write, because the write is the serialization boundary and a prior `resolve()` is a value the caller already holds while time keeps advancing. The check constraint does not cover this: it bounds `idle_expires_at` against `absolute_expires_at`, and says nothing about either against `now` |
| **A break-glass session receiving the ordinary idle window** (added 2026-08-15; **mechanism corrected three times on 2026-08-15**, by the second and third session-lifetime reviews and by the idle-policy-construction review) | The idle duration is **not something a caller supplies, not something a caller constructs, and not carried by an object a caller can subclass.** The duration is chosen inside the conditional write by `CASE auth_method` from the `SessionPolicy` the repository derived from its `SessionSettings` — the configured N-06 value for `discord_oauth`, the configured N-15 value for `webauthn` and `recovery_grant`, classified by the explicit `_SESSION_CLASSES` table. Three earlier versions of this row named mechanisms that did not hold: (1) an `expected_auth_method` equality predicate, which refused a *false method* while accepting a break-glass row's **true** method beside N-06's duration; (2) an injected policy whose public dataclass constructor accepted any complete, duplicate-free, positive mapping — including one giving every method the ordinary window; (3) a policy with no public constructor whose `from_settings()` read an unvalidated `SessionSettings` (F1) and whose overridable `__iter__` was what the SQL was generated from (F2), with a service free to hold a second policy (F3). What holds now is structural rather than guarded: `SessionSettings` cannot exist outside the register, there is no object that pairs a method with a duration, the repository derives its bounds instead of accepting them, and the service reads the repository's |
| Privilege escalation without rotation | The fingerprint is recomputed from the freshly resolved capability set (N-09/N-10), not read from the session |
| A break-glass session gaining Council | Capability resolution short-circuits on `auth_method != 'discord_oauth'` and returns exactly `{platform_administrator}` (N-12, N-65) |
| A break-glass session **arranging** for a later ordinary session to gain Council | The short-circuit above cannot see this, and the first revision of this document wrongly treated it as covered. It is stopped instead by N-67 and the provenance guard: a mapping written under continuity scope may name only `platform_administrator`, and administrator capability derived only from such mappings is itself continuity-scoped (schema §8.1). Enforced by an application check, a check constraint and the N-65 route surface, independently |
| Reusing a rotated session's cookie | The old row is revoked in the same transaction that creates the new one |
| A session acquiring **two** successors, so one login has two live descendants (added 2026-08-14, OD-44 §8) | `UNIQUE (rotated_from_session_id) WHERE rotated_from_session_id IS NOT NULL`, plus the locked predecessor read that revokes the row it is rotating. Two concurrent rotations meet at the row lock: the loser re-evaluates after the winner commits, matches zero rows and is refused |
| A rotation crossing an account, an authentication method or an OAuth binding (added 2026-08-14, OD-44 §8) | Two composite foreign keys into the predecessor row make the successor's `(platform_account_id, auth_method)` and `oauth_transaction_id` the predecessor's own (schema §9.1); the repository additionally refuses a caller whose resolved account or method disagrees, so the outcome is a typed refusal rather than an integrity error |
| Labelling an arbitrary session a rotation to obtain a second session for an already-completed transaction (added 2026-08-14, OD-44 §8) | The binding foreign key requires the successor's transaction id to be the one its named predecessor carries, so there is no session to attach to except that login's own chain. No creation path accepts a rotation label at all: `rotated_from_session_id` is written only by `rotate()` |
| Rotating a revoked, expired or already-rotated session | The locked predecessor read requires `revoked_at IS NULL` and no existing successor. Liveness is the one rule PostgreSQL cannot state declaratively, so it is enforced in that single operation |

### Failure behaviour

- **Restart:** sessions are database rows; a restart logs nobody out. That is a
  requirement, not a nicety — a restart during a deploy must not invalidate a
  Council member's in-progress import.
- **Retry / double submit:** rotation is idempotent per request because the
  fingerprint comparison is a no-op when nothing changed.
- **Concurrent rotation of one session** (added 2026-08-14): exactly one
  successor is created and the other caller is refused. The predecessor's row
  lock decides it, not the order the threads were scheduled in.
- **Provider outage:** membership cannot be refreshed. Within N-10's 15-minute
  grace, protected **reads** proceed on the last successful result; mutations fail
  immediately; after the grace, everything fails closed with VM-03. The session
  itself stays `active` — it is authentication, and authentication did not fail;
  what failed is authorization freshness.
- **Audit failure** on logout: the revocation and the audit event share a
  transaction. If the audit write fails, the logout fails and the user is told to
  retry, because an unrecorded revocation is exactly the record an incident
  investigation needs.

## SM-03 — Break-glass authentication

### States

```text
  ┌──────────────┐   options    ┌───────────────┐  verify ok   ┌─────────────────┐
  │   anonymous  │ ───────────▶ │  challenged   │ ───────────▶ │ emergency active│
  └──────────────┘              └───────┬───────┘              └────────┬────────┘
                                        │ fail / expire                 │ N-15
                                        ▼                               ▼
                                  ┌──────────┐                    ┌──────────┐
                                  │ refused  │                    │ expired  │
                                  └──────────┘                    └──────────┘

  recovery path:  grant issued (C-01) ─▶ live ─▶ consumed ─▶ emergency active
                                            └─▶ expired / invalidated
```

### Transitions — WebAuthn

| From | To | Trigger | Mechanism |
|---|---|---|---|
| `anonymous` | `challenged` | R-07, within N-32 | Challenge row with an N-04 lifetime |
| `challenged` | `emergency active` | R-08 verifies signature, RP ID, origin (N-60), user verification, and a non-decreasing `sign_count` | Session insert with `auth_method = 'webauthn'`, N-15 bounds |
| `challenged` | `refused` | Any check fails, or the challenge is expired/consumed | Conditional consumption; the response says only "failed" (VM-04) |

### Transitions — recovery grant

| From | To | Trigger | Mechanism |
|---|---|---|---|
| — | `live` | C-01 on the host | Insert; the partial unique index (N-61) invalidates any prior live grant in the same transaction |
| `live` | `consumed` | R-09 with the matching token | `UPDATE … WHERE token_hash = $1 AND consumed_at IS NULL AND invalidated_at IS NULL AND expires_at > now() RETURNING` |
| `live` | `expired` | 10 minutes (N-14) | Time; enforced in the consumption statement |
| `live` | `invalidated` | C-02, or a newer grant | Explicit update |

### Forbidden

| Forbidden | Mechanism |
|---|---|
| Replay of a consumed grant | Zero rows on the second conditional update |
| Use after expiry | Same statement's `expires_at > now()` |
| Use for anything but emergency login | `CHECK (purpose = 'emergency_login')`, and the login path filters on it |
| A grant issued over HTTP | **No route exists** (route contract §1). Issuance is C-01, host-local, requiring existing host authority |
| Two live grants | Partial unique index (N-61) |
| Break-glass acquiring Council, character ownership or import authority | Capability resolution (SM-02) plus N-65's route-level refusal; both are tested independently |
| Break-glass acquiring that authority **later**, through a mapping it created and an ordinary login | N-67's allowlist refuses the mapping; the check constraint refuses it again; and provenance makes administrator capability derived from an emergency mapping continuity-scoped, so the second hop is refused too (schema §8.1). TC-BG-05a…05e prove the whole sequence, not each hop in isolation |
| A continuity-scoped session ratifying its own mapping | R-38 requires `auth_method = 'discord_oauth'` **and** administrator scope `full`; the trigger permits the `provenance` transition in one direction only, and only with `ratified_by_account_id` set in the same statement |
| Enrolling a credential from a break-glass session | **No route exists**; enrollment is C-03, host-local |
| The token appearing in a log, audit row or response | The token is never stored; audit records name the grant **record id** (delivery plan §9.7) |

### Failure behaviour

- **Discord outage:** irrelevant to this machine by construction — that is the
  requirement of OD-43. No step here contacts Discord.
- **Lost response** after consumption: the grant is spent and the session exists;
  the operator issues a new grant with C-01. The audit record shows one
  consumption, so the operator can tell a lost response from an attack.
- **Restart** between R-07 and R-08: the challenge is a database row; the flow
  continues.
- **Concurrent consumption:** one wins, the other gets zero rows.
- **Audit failure:** session creation and the audit event share a transaction, so
  an unrecordable emergency login does not occur. This is the strictest place in
  the platform for that rule, and deliberately so.

## SM-04 — External identity link, unlink and provider retirement

### States

```text
        ┌──────────────┐  strong reauth + confirm  ┌──────────┐
        │  unlinked    │ ────────────────────────▶ │  active  │
        └──────────────┘                           └────┬─────┘
                                                        │ unlink (R-37) / provider retirement
                                                        ▼
                                                  ┌───────────┐
                                                  │  retired  │  (terminal; row is kept)
                                                  └───────────┘
```

### Transitions

| From | To | Trigger | Mechanism |
|---|---|---|---|
| `unlinked` | `active` | First login on a provider with no existing identity → a new account; or an explicit link to an existing account after strong reauthentication and audited confirmation (N-16) | Insert; `UNIQUE (provider_key, subject)` |
| `active` | `retired` | R-37, or an operator provider retirement | `UPDATE … SET state='retired', retired_at, retired_reason` |

### Forbidden

| Forbidden | Mechanism |
|---|---|
| Two accounts holding the same `(provider, subject)` | The unique constraint, which covers retired rows |
| Re-linking a retired subject to a **different** account | Same constraint. Re-linking to the *same* account is an explicit, audited administrative action |
| Linking by display name, username or email | No such column exists on `external_identities` (schema §5) |
| Unlinking the last usable identity | The application refuses when no other `active` identity exists and no reviewed recovery route applies (delivery plan §9.5). For the protected account, enrolled WebAuthn credentials count as that route; for an ordinary member they do not |
| Deleting an identity row | No delete path exists; `RESTRICT` on the FK and the absence of a use case |
| A break-glass session performing either | N-65; R-36/R-37 refuse `BG`, and by route contract §3.3 they refuse `AC` on the same cell |
| Silent account merge | There is no merge operation anywhere in the inventory. Two accounts stay two accounts |

### Failure behaviour

- **Provider retirement** (a whole provider withdrawn): every identity for that
  `provider_key` moves to `retired` in one transaction; accounts left without an
  active identity are reported, and the report is a **blocking** operational item,
  not an automatic re-link. Audit attribution keeps resolving through the retired
  rows (migration contract §8).
- **Subject reuse by a future OIDC provider:** the constraint prevents a *silent*
  takeover — the second person's subject collides and the login is refused rather
  than being merged into the first person's account. This is recorded as residual
  risk RR-04, because refusing is safe but is also a support incident.
- **Audit failure:** link and unlink each write their audit event in the same
  transaction as the state change.

## SM-05 — Reconciliation job: queue, lease, preview, confirmation, apply

This is the machine delivery plan §8 specifies. States are exactly N-27's six.
`kind` (`preview` or `apply`) selects the work; the lifecycle is identical, which
is what allows one set of recovery tests to cover both.

### States and transitions

```text
                    R-42 / R-46
                         │
                         ▼
                   ┌──────────┐  claim (SKIP LOCKED)   ┌───────────┐
                   │  queued  │ ─────────────────────▶ │  running  │
                   └────┬─────┘ ◀───────────────────── └─────┬─────┘
                        │   lease expired AND attempts < 3   │
       cancel / stale   │        (reaper, one statement)     │
                        │                                    │
                        │            ┌───────────────────────┼──────────────────┐
                        ▼            ▼                       ▼                  ▼
                  ┌───────────┐ ┌─────────┐          ┌────────────┐      ┌──────────┐
                  │ cancelled │ │  stale  │          │ completed  │      │  failed  │
                  └───────────┘ └─────────┘          └────────────┘      └────▲─────┘
                                                                              │
                                        lease expired AND attempts = 3 ───────┘
                                        (the SAME reaper statement, other branch)
```

**What `attempts` means, once:** the number of **claims** made against this job.
The claim statement increments it; nothing else writes it. `N-43` caps it at 3,
`CHECK (attempts BETWEEN 0 AND 3)` enforces the cap, and
`CHECK (state <> 'queued' OR attempts < 3)` enforces the consequence — *a queued
job always has a remaining attempt*. There is no fourth claim, in the design or
in the vocabulary.

| From | To | Trigger | Mechanism |
|---|---|---|---|
| — | `queued` | R-42 (`preview`) or R-46 (`apply`) | Insert with `attempts = 0`; `request_key` unique; N-42 admission bound; for `apply`, the one-live-apply partial unique index |
| `queued` | `running` | Worker claim | The `FOR UPDATE SKIP LOCKED` statement in schema §10.1; sets lease, increments `attempts`, and matches only while `attempts < 3` |
| `running` | `running` | Heartbeat ≤ every 20 s (N-23) | `UPDATE … SET heartbeat_at, lease_expires_at = now() + 60s WHERE id = $1 AND lease_owner = $2` |
| `running` | `queued` | Lease expired **and** `attempts < 3` | The reaper's requeue branch (schema §10.1). Clears the lease; the job keeps its `attempts` and is claimable again |
| `running` | `failed` | Lease expired **and** `attempts = 3` | The **same statement's** other branch: `failure_code = 'attempts_exhausted'`, `finished_at = now()`. This replaces the first revision's unreachable "4th claim" transition |
| `running` | `queued` \| `failed` | Worker self-abandon at N-45's hard cap or on the kill switch | The same two-branch update, under `AND lease_owner = $2`; zero rows if the reaper already acted |
| `running` | `completed` | Work finished **and** its result row committed | Result row inserted, then the job updated in the **same transaction**; `CHECK ((state='completed') = (result_id IS NOT NULL))` |
| `running` \| `queued` | `stale` | `scope_fingerprint` no longer matches, folder changed (R-41), profile version changed, or N-46 elapsed | Single update setting `stale_reason` |
| `running` \| `queued` | `cancelled` | `cancel_requested_at` observed (queued: immediately; running: at the next heartbeat) | Update; forbidden once an apply has committed |
| `running` | `failed` | Deterministic refusal (`parse_refused`, `artifact_unavailable`) | Update with `failure_code`, immediately, whatever `attempts` says. A refusal that will recur is not retried |

### Why the first revision could not work

Recorded because the correction is only checkable against the defect. The reaper
requeued `WHERE … attempts < 3`, and `running → failed` was described as
happening on "the 4th claim". Those two statements cannot both be satisfied:

- after the third lease expired with `attempts = 3`, the reaper's predicate
  excluded the row, so it stayed **`running` with no worker and no lease** —
  permanently, since nothing else transitions a `running` job;
- and had the reaper requeued it, the fourth claim would have set `attempts = 4`
  and violated `CHECK (attempts <= 3)`, aborting the worker's transaction rather
  than failing the job.

The job was therefore unreachable from every terminal state, which is the exact
opposite of what a retry cap is for. The fix is not a larger cap: it is putting
the terminal transition in the hand that observes the expiry, so exhaustion is
detected by the same statement that would otherwise retry.

### Forbidden transitions

| Forbidden | Mechanism |
|---|---|
| Any terminal state → any other state | `CHECK` that terminal states have `finished_at`, plus the application's single-statement guards on `state IN ('queued','running')` |
| `completed` without a durable result | The `result_id` check constraint (delivery plan §8.7) |
| Two workers on one attempt | `FOR UPDATE SKIP LOCKED` claim; the lease is proof of ownership and every write carries `AND lease_owner = $2` |
| Two applies of the same input both committing | `uq_snapshot_imports_applied_input` (existing) and `snapshot_imports.request_key` (existing). The job-level index only prevents the wasted work |
| An expired lease being read as failure | The reaper returns the job to `queued` while an attempt remains; only exhaustion produces `failed` (N-23, N-43) |
| A job remaining `running` after its lease expires | The reaper's statement has no predicate that can exclude an expired lease: both branches of the `CASE` transition the row out of `running`. Assuming a live reaper, lease-expiry recovery is bounded by `N-23 + N-44` per claim, at most ≈225 s across three expired claims; this excludes queue waiting, successful execution time and N-45's separate runtime cap. TC-JOB-13 measures it |
| A `queued` job with no attempt left | `CHECK (state <> 'queued' OR attempts < 3)` |
| A fourth claim | The cap, the claim predicate `attempts < 3`, and the fact that the reaper never requeues an exhausted job |
| Two reapers both transitioning one job | `FOR UPDATE SKIP LOCKED` in the reaper's sub-select |
| A worker stamping a verdict on a job it no longer holds | Every worker write carries `AND lease_owner = $2`; a lost lease means zero rows |
| Cancelling a committed apply | The apply's commit sets `state='completed'`; the cancel statement filters `state IN ('queued','running')` and matches zero rows, answering `409` (route contract §6.1) |
| Applying on a stale scope | Apply re-checks the fingerprint **inside** its own transaction, after re-resolving Council authority. A mismatch aborts before any write |
| Applying without current Council authority | `SnapshotImportService.apply` re-resolves through `AuthorizationPort` at apply time — the module's documented reason for existing |
| Raw artifact bytes reaching a result, response, log or job payload | The result columns hold counts, codes and identifiers only (schema §10.2; delivery plan §8.9) |

### Failure behaviour

- **Process restart mid-run:** the worker dies holding a lease. No heartbeat
  arrives; within `N-23 + N-44` the reaper acts — requeueing while an attempt
  remains, or failing the job with `attempts_exhausted` if this was the third. A
  worker claims a requeued job as attempt *n+1*. **No apply is duplicated**,
  because the durable effect is fenced by `uq_snapshot_imports_applied_input` and
  the request key, not by the job's state. If the previous attempt had already
  committed, the retry finds the existing import and returns it as a duplicate
  result.
- **Lost worker that never comes back** (the host is gone, the process is
  `SIGKILL`ed, the container is destroyed): identical, because nothing in the
  recovery path asks the worker anything. Three lease expiries later the job is
  `failed` with `attempts_exhausted` and the Council member sees a terminal state
  with a correlation id, rather than a spinner over a job nobody is running.
- **Two reapers running at once** — during a rolling restart, or if an operator
  starts a second worker: each expired job is transitioned by exactly one of
  them (`FOR UPDATE SKIP LOCKED`), `attempts` is incremented only by claims so it
  cannot be double-counted, and the requeue/fail decision is taken inside the row
  lock. Neither reaper can see a half-transitioned job. TC-JOB-13 runs two real
  reaper connections against one expired lease and asserts exactly one
  transition.
- **Reaper failure or absence:** if no reaper runs, expired jobs stay `running`
  until one does. That is a liveness dependency on a process, stated rather than
  hidden: the reaper is part of `freedom-worker` (N-40), the health check reports
  the age of the oldest expired lease (VM-16), and monitoring alerts on it. There
  is no correctness consequence — nothing reads a `running` job as a result — but
  a Council member waits.
- **Lost response** to R-46: the browser does not learn the job id. The user
  retries; the same `request_key` returns the existing job (delivery plan §8.6).
  Two browsers doing this concurrently both land on the same job.
- **Expired lease with work still running** (a slow parse, not a dead worker): the
  reaper may requeue while the original attempt is still executing. This is the
  classic double-execution window, and it is safe here for one reason worth
  stating: **execution is not the durable effect**. A preview writes only its own
  result row, keyed by job; an apply's durable effect is fenced by the existing
  unique constraints. The second executor's commit fails and it reports a
  duplicate. N-45's hard cap is set to 300 s specifically so the window is bounded
  by the process, not only by the constraint.
- **Concurrent apply from two browsers:** both hit `uq_reconciliation_jobs_one_live_apply`;
  the second receives the first's job. One durable effect, one audit success event
  (plan §12 Phase 3 mandatory test).
- **Audit failure during apply:** the existing Phase 2 rule holds unchanged — the
  audit event is in the apply transaction, so an audit failure rolls back the state
  change, and a refusal event may be written afterwards in its own transaction with
  the same correlation ID and no claim of partial state (plan §6.5).
- **Provider outage during apply:** the apply re-resolves Council authority. If
  Discord is unreachable and the N-10 grace is exhausted, authority cannot be
  confirmed and the apply is **refused** — mutations fail immediately during an
  outage (N-10). It does not proceed on a cached role.
- **Kill switch engaged mid-run:** the worker stops claiming new jobs and finishes
  or abandons the current attempt at its next heartbeat; an abandoned attempt is
  recoverable, not failed.

### Cancellation semantics, stated exactly

`cancel_requested_at` is a request. It cancels a `queued` job immediately, a
`running` job at its next heartbeat, and **never** an apply that has committed.
It does not erase history: the job's audit events and, if the apply committed, the
`snapshot_imports` row remain (delivery plan §8.8).

## SM-06 — Membership and role projection (supporting machine)

Included because SM-02's outage behaviour is meaningless without it.

```text
  ┌──────────┐  refresh ok   ┌───────┐  age > N-09   ┌──────────┐
  │  absent  │ ────────────▶ │ fresh │ ────────────▶ │  stale   │
  └──────────┘               └───────┘               └────┬─────┘
       ▲                          ▲  refresh ok           │ refresh fails
       │                          └───────────────────────┤
       │                                                  ▼
       │                                          ┌───────────────┐
       │       grace exhausted (N-10)             │ within grace  │
       └──────────────────────────────────────────┴───────────────┘
```

| Rule | Value |
|---|---|
| Fresh | `observed_at` within N-09 (5 minutes) |
| Stale, refresh succeeds | Becomes fresh; if the capability set changed, SM-02 rotates the session |
| Stale, refresh fails | Protected **reads** proceed for at most N-10 (15 minutes) from the last **successful** observation; every mutation is refused immediately |
| Grace exhausted | Every protected route answers VM-03 with `503`. Fail closed |

Forbidden: treating a cached role as proof after the grace; refreshing on the
request path in a way that lets a slow provider hold a database transaction open
(the refresh happens before the transaction, with its own timeout); and any code
path that reads a role from the session instead of the projection.

## SM-07 — Role-capability mapping provenance

Added by the P3.0 remediation. Without it, "a break-glass session cannot acquire
Council" is a statement about one session, and the attack is a statement about
two.

### States

```text
                 created by a full-scope admin
                 on an ordinary-provider session
   ────────────────────────────────────────────────▶ ┌──────────────────┐
                                                     │ active/ordinary  │
   created under continuity scope                    └────────┬─────────┘
   ──────────▶ ┌───────────────────────────┐   R-38           │ R-34
               │ active/emergency_continuity│ ───ratify──────▶ │
               └────────────┬───────────────┘                 │
                            │ R-34 (only if capability =       ▼
                            │ platform_administrator)   ┌──────────────┐
                            └──────────────────────────▶│   revoked    │
                                                        └──────────────┘
                       ┌──────────────────┐
                       │ protected        │  inserted by migration; terminal.
                       │ (ordinary)       │  No transition exists at all.
                       └──────────────────┘
```

### Transitions

| From | To | Trigger | Mechanism |
|---|---|---|---|
| — | `active/ordinary` | R-33 by a caller with administrator scope `full` | Insert with `created_under_scope='full'`, `provenance='ordinary'` |
| — | `active/emergency_continuity` | R-33 by a caller with scope `emergency_continuity` | Insert; the check constraint permits only `capability = 'platform_administrator'` |
| — | `protected` | Migration only | Insert-once trigger; a second protected row is refused |
| `active/emergency_continuity` | `active/ordinary` | R-38 | `UPDATE … SET provenance='ordinary', ratified_at=now(), ratified_by_account_id=$1` under the one-way trigger |
| `active/*` | `revoked` | R-34 | `UPDATE … SET active=false, revoked_at, revoked_under_scope`; the allowlist check constrains a continuity-scoped revoker to `platform_administrator` rows |

### Forbidden

| Forbidden | Mechanism |
|---|---|
| `ordinary` → `emergency_continuity` | The one-way `BEFORE UPDATE` trigger. A mapping cannot be pushed back across the boundary to disguise where it came from |
| Ratification by a continuity-scoped or break-glass caller | R-38's two preconditions, plus the trigger's requirement that `ratified_by_account_id` be set |
| Re-ratification | `CHECK (ratified_at IS NULL OR provenance = 'ordinary')` plus the trigger refusing a second transition |
| A continuity-scoped caller writing any capability but `platform_administrator` | `CHECK (created_under_scope = 'full' OR capability = 'platform_administrator')`, plus the service check, plus N-65 |
| Any change to the protected row | The 0002-style `BEFORE UPDATE OR DELETE` trigger, for every caller including the schema owner |
| A revocation removing the last route to administrator capability | Not forbidden, and deliberately so: the protected mapping cannot be revoked, so the last route always survives. Capability resolution is a union, so revoking any other mapping cannot subtract it (OD-24) |

### Failure behaviour

- **Restart:** every state is a row; nothing is held in memory.
- **Concurrent create of the same `(guild, role, capability)`:** the partial unique
  index admits one; the second receives `409` with the current state.
- **Concurrent ratify and revoke:** the mapping's optimistic `version` makes one
  of them stale; the loser is refused `409` and re-reads. Neither can produce a
  ratified-and-revoked row, because both write `version`.
- **Audit failure:** the mapping change, its `audit_events` row and its
  `role_capability_mapping_events` row share one transaction. An unrecordable
  capability change does not happen — the same rule SM-03 applies to emergency
  logins, for the same reason.
- **Refusals are recorded too**, in `role_capability_mapping_events` with the
  attempted capability and a refusal code, in their own transaction after the
  rollback, carrying the same correlation id.
