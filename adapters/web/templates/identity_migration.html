{% extends "base.html" %} {% block title %}Identity migration — Council — Freedom Blades{% endblock %} {% block content %} {# VM-10, R-28, and the two controls R-29/R-30 carry. Three things on this page are evidence and confer nothing: the Sheet player name, the Sheet Discord name and the Active DM flag. A username is not a snowflake and usernames change; one Discord name is recorded per player while several people may be authorized on one character; and `Active DM` never grants capability (OD-18). The only identity here is the snowflake. **A confirmation is the activation** (migration contract §7.2 as amended by change-log entry C-P3.2-A, OD-46). Confirming a proposal creates that character's access row immediately, in the same transaction as the decision and its audit events. So this page has four decision states and not five: outstanding evidence, ambiguous/unresolved evidence, a confirmed proposal, and a rejected one. There is no "confirmed but not applied" row, no apply outcome and no run apply status, because there is nothing between a confirmation and the row it writes. **A confirmed row also says whether its link is active now** (change-log entry C-P3.2-C). Council may revoke a link through R-26 afterwards, and the confirmation stays confirmed — the decision, its decider and its reason are history and are not rewritten (§7.5). What changes is the access row, so this page reads `character_access.active` for the **exact** row that confirmation created and says `is active now` only when it is. Another active link on the same character or the same account is a different row and cannot answer this question. Nothing is auto-confirmed, nothing is confirmed in bulk — there is no bulk control on this page and adding one would remove the per-proposal decision the contract requires — and an ambiguous or unresolved proposal has no confirm control, because it has no snowflake to link to. The server refuses it regardless of what the browser submits. The confirm form states what it is about to do before doing it: the character, the stable Discord identity, the access kind the confirmation will create, and the required reason. It carries the character's optimistic `version`, exactly as R-25's grant form does, because a confirmation now changes the character and must not be applied on top of somebody else's change. The reject form carries no version: a rejection changes no character. The totals are §7.4's control totals, shown to the person doing the confirming rather than only in a report they may not read. #}
